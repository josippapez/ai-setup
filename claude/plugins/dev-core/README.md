# Interactive MCP Claude Plugin

Everyday defaults for Claude Code: repo grounding, the always-on engineering rules, core skills, and the specialist agents. Claude-compatible mirror of the OpenCode `interactive-mcp` custom plugin, which keeps the older name.

- **Repo grounding comes from the separate `repo-docs` plugin, not from this one.** `find_docs`/`list_docs`/`read_doc`/`find_libs` and the bundled CodeGraph code-graph server (`codegraph_explore`) live in `claude/plugins/repo-docs`, shared with `orchestrate` so both use one MCP server and one tool namespace (`mcp__plugin_repo-docs_repo-docs__*`) instead of each bundling an identical copy. `claude/install.sh` installs `repo-docs` automatically alongside this plugin; if its tools are not callable, tell the user to run `claude plugin install repo-docs@ai-setup`. See `claude/plugins/repo-docs/README.md`.
- `.mcp.json` registers `interactive` (`@rawwee/interactive-mcp`, a question tool subagents can reach since Claude Code withholds `AskUserQuestion` from them), plus bundled third-party MCP servers that should be available by default in every project: `context7` (`@upstash/context7-mcp`) and `chrome-devtools` (`chrome-devtools-mcp`). These ship enabled with the plugin so they need no per-machine MCP config. Project- or secret-specific servers (e.g. Figma, a local Storybook endpoint) are intentionally kept out of the plugin and live at user scope in `~/.claude.json`.
- **WCAG lookups are a CLI, not an MCP.** Accessibility criteria/techniques/failures come from `@rawwee/wcag-cli`, invoked over Bash and documented by the bundled `accessibility` skill. A skill + on-demand CLI costs nothing until used, whereas an always-registered MCP spawns a subprocess every session — the same pattern as `opensrc` and `rtk`. Prefer this shape for any *stateless reference lookup*; keep an MCP only where the server holds real state (a warm index, a browser session), as `repo-docs` and `chrome-devtools` do.
- `skills/` mirrors the OpenCode skills.
- `rules/` holds always-on rules bundled with the plugin (llm-coding-guidelines, opensrc, git-move, proactive-execution, codegraph). Claude Code has no native plugin "rules" loader, so `hooks/inject-rules.cjs` reads every `rules/*.md` and emits them as `additionalContext`. It is registered for **two** events, because SessionStart context is not inherited by subagents:
  - `SessionStart` — the main conversation, on every source (startup/resume/clear/compact/fork), so the rules survive compaction. It is the only compaction-adjacent hook that can re-inject context; PostCompact is side-effect only.
  - `SubagentStart` — each subagent, before its first prompt ([hooks reference](https://code.claude.com/docs/en/hooks#subagentstart)). Without it the rules reach the main agent only: measured with a no-tools probe subagent, `~/.claude/CLAUDE.md` text was present in its context while SessionStart-injected rules were absent, and the subagents doc omits SessionStart output from what subagents receive. Confirmed working after wiring it up: the same probe quoted back all four shards and every rule, including the `SubagentStart`-only wording "they apply to this task". So `CLAUDE.md` needs no copy of any rule — it stays for CLI notes only.

  Both events shard the bundle under the 10,000-character `additionalContext` cap, and `hooks.json` registers 8 slots per event (4 in use). The `hookEventName` in each reply must match the event that fired, so the script takes the event as its second argument and exits silently on an unknown one. **Cost:** the full bundle is about 6.2k tokens, paid once per session and again on every subagent spawn. Narrow it with a `SubagentStart` matcher (it filters on agent type) if that becomes the wrong trade.

  Trade-off vs. `~/.claude/rules/`: hook-injected rules don't support per-file `paths:` frontmatter scoping — they load unconditionally.
